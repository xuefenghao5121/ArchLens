# L3 Criteria Guard——判据有效性与保真度对称标准流程

## 为什么存在这个 skill

真实事故（2026-11-13，platform/lessons/2026-11-13-l3-comparative-fidelity.md）：L3 用
gem5 默认模型（未校准 opLat）测得的基线数字设立绝对阈值，方案侧却按 RTL 实测注入测量——
跨基架对比必然"方案慢"，据此下的"拒绝硬件路线"裁决无效，靠用户两次人工纠正才发现。
两道防线（gate、人类批准）都没拦住：gate 无字段无规则，批准问题没暴露阈值来源假设。
本 skill 是把那次教训变成的**前置结构检查**。

## 基架分级词汇（先记住）

| 级 | 含义 | 例子 |
|---|---|---|
| **F0** | 仿真器默认参数，未校准 | gem5 FUPool 默认 opLat/吞吐 |
| **F1** | 契约拍定参数 | L4 契约里 assumed 的时延/占用 |
| **F2** | RTL 实测背书 | tick_once 差分实测的单元时序，经保真对账注入 |
| **F3** | 解析模型推导 | 地板模型、成本模型拟合值 |

## 六步标准流程（顺序执行，不许跳）

### 第 1 步：数字溯源表

列出本次将引用的**每一个**测量数字，逐个登记：

```
| 值 | 含义 | 产出它的运行/包 | 时延模型 | 基架级 |
```

不许跳过"看起来像真值"的数字——基线数字恰恰最容易漏标。

### 第 2 步：基架标注

按上表给每个数定级（F0-F3）。拿不准就往低定（更保守）。同一个包里的数字可能不同级
（例如 L2 的周期数是 F0，但其 RTL 注入统计是 F2）。

### 第 3 步：判据锚点检查（先于对称性——判据和"什么"比）

L3 判据只允许两类锚点：

1. **上游瓶颈特征量**（L2 归因产出）：瓶颈份额、指令流构成、依赖链深、束缚约束位置等。
   判据形式如"瓶颈份额从 X% 降到 Y% 以下""植入/归因的指令流被机制替代至≈0""束缚约束迁移
   且被重新定位"——**通过与不通过，答案完全在解决方案系统内部**，不依赖任何外部方案的表现。
2. **方案自身机制参数空间**（同框开关对比）：窄口 vs 宽口、K=1 vs K=4、lat 敏感性——量化
   expected_mechanism 是否兑现，同样是系统内部对照。

**非法锚点**：任何其他方案的性能数字（gem5 基线、软件优化上界、上一代方案）——无论基架
是否对称，都不得作为 L3 的通过性阈值。方案间排名是 L8/横向评估的事，且必须同基架；
L3 的问题是"**优化是否解决了已确认的瓶颈**"，不是"是否跑得比别人快"。

### 第 4 步：对称性检查（判据门）

对将要设立的**每条**判据问：它对比的两侧数字基架是否同级？

- **F2 vs F2（或同 F1 框内）**：可以立绝对阈值判据
- **基架不对称（如 F2 方案 vs F0 基线）**：**禁止**设立绝对成立/拒绝阈值**。改用以下三种合法形态之一：
  1. **瓶颈消除检验**：同一系统优化前后的瓶颈指标对照（如瓶颈份额迁移、占用分布变化）——同框，永远合法
  2. **同框开关对比**：同一系统内 parametric A/B（窄口 vs 宽口、K=1 vs K=4）——同框，测的是优化自身边际价值
  3. **校准用途标注**：跨基架数字只能用于"校准低基架模型"的方向参考，输出物必须写明"非裁决依据"

### 第 5 步：判据三问（写进给人类的批准问题里）

1. 每个阈值数字产自哪个时延模型（基架级）？
2. 方案侧与基线侧基架是否对称？不对称时换成了哪种合法形态？
3. 这条判据回答的是 L3 的问题（**优化是否解决已确认瓶颈**）还是别的问题（绝对性能排名）？

预期机制必须附**瓶颈消除的可观测指标**（如"L2 归因的瓶颈份额从 X% 降到 Y% 以下"），
不能只有终态周期。

### 第 6 步：写入与门禁

```json
"acceptance_criteria": {
  "criteria": [...],
  "measurement_frames": {
    "<每个阈值数字>": {"frame": "F0|F1|F2|F3", "source": "产出运行的包/点"}
  }
}
```

`wf gate` 已强制：L3 有 acceptance_criteria 必须带 measurement_frames；L8 comparisons 每项
必须带 frame。缺字段=拦截。

## 红线（违反任何一条=判据无效）

1. L3 判据**不得**锚定其他方案的性能数字（基线/软件上界/上一代方案）——无论基架是否对称
2. 不同基架的绝对周期对比**不得**作为成立/拒绝的裁决依据
3. 预期机制不得只写终态周期，必须含瓶颈消除指标
4. 撤回/修改判据必须决策留痕 + `contradicted_by`/`supersedes` 入 DAG，禁止静默改
5. 精确侧（F2）与拍定侧（F0）混用时，不得用拍定侧数字给精确侧"定罪"——拍定侧不暴露自己的误差
6. **层间交接（handover/recommendation）同样受锚点约束**：上游给下游的建议里不得出现
   "与某方案比/打赢某数字"式的对比锚——真实事故（2026-11-14 审视）中污染正是经由
   L2b/L6 的交接建议传入 L3 判据的，而不是经由判据字段本身
7. **平台解空间 = 微架构/硬件干预**：L3 候选必须是硬件向方案（单元时延/转发/阵列/
   端口/融合等微架构资源干预，经 L4 契约→L5 RTL→L6 注入落地）；benchmark/kernel 本身的
   软件优化（指令重排、批量化调度、寄存器分配等 kernel 工程）**超出平台 agent 工作范围**，
   只能降级为对照组参照臂（F 标签、不进判据、不作交付物）——真实事故（2026-11-16）：
   迭代 2 L3 曾把纯软件拆链候选选为主方案，经用户纠正重定范围
